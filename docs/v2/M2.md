## Scope

M2 establishes the clean v2 backend foundation under `src/backend/v2`; legacy `src/backend` remains reference-only.

Implemented:

- Go 1.25 module using standard `net/http` and direct pgx/v5;
- PostgreSQL schema for users, roles, credentials, identities, invitations, posts, media, tags, nested comments, votes, and durable media jobs;
- immutable numeric relational IDs; usernames never foreign keys;
- explicit post release/content-filter state and media processing state;
- post-ID cursor pagination, never OFFSET;
- bounded around-post reconstruction;
- real search lexer/parser/AST for included/excluded tags and score predicates;
- parameterized SQL with a closed score-operator enum;
- stable JSON error envelope;
- initial PostgreSQL pool cap 8 and 3-second request/DB deadline;
- no Redis dependency without a measured ephemeral use.

Endpoints:

- `GET /healthz`
- `GET /api/v2/feed?before=<post-id>&limit=<n>&q=<search>`
- `GET /api/v2/posts/<id>/around?radius=<n>&q=<search>`

## Visibility semantics

`feed.Query.Filters` / `feed.AroundQuery.Filters` represent the content types allowed for the request, not search context. The current unauthenticated skeleton defaults this set to SFW; future authenticated request context will supply the real allowed set.

For around-post reconstruction:

- newer/older neighbors apply allowed visibility plus search predicates;
- the selected canonical post applies allowed visibility but ignores search predicates;
- release/deletion/media-readiness constraints always apply.

This preserves canonical reconstruction without allowing search state to hide the selected post and without bypassing visibility authorization.

## Validated query decisions

### Bounded media lookup

The original old-cursor join scanned about 50k media rows. Bounded per-post `media_pkey` lookup reduced the same-run old-cursor plan from 9.568 ms to 0.156 ms in Run 5, with 61 media lookups. Keep this shape.

### Included-tag filtering

Resolve normalized tag name to immutable `tags.id`, then constrain active `post_tags.tag_id`.

The existing partial index is sufficient:

`post_tags_tag_post_active_idx (tag_id, post_id DESC) WHERE removed_at IS NULL`

Run 5 same-run results:

- tag + score: 71.240 -> 1.563 ms;
- tag + excluded tag + score: 70.068 -> 1.899 ms;
- included assignment scan: about 158,680 -> 1,587 rows.

No additional search index is justified by current evidence.
