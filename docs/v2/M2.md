## Scope of this slice

This slice establishes a clean v2 backend module at `src/backend/v2`. The legacy `src/backend` (`wallium`) implementation remains reference-only and is intentionally not extended.

Implemented foundation:

- Go module isolated from v1 backend code
- standard-library `net/http` API surface; no web framework
- PostgreSQL through direct `pgxpool`
- default PostgreSQL pool cap of 8 connections
- explicit 3-second request contexts for API database work
- immutable numeric IDs throughout relational data
- users separate from credentials and external identities
- invitation policy separate from credentials/identity
- posts with explicit content filter and release state
- one media metadata row per post for the current product model
- tags plus auditable add/remove metadata
- nested comments and vote foundation
- PostgreSQL-authoritative durable media job table/state
- ID-descending cursor feed, never OFFSET
- bounded around-post query for deep-link reconstruction
- real search lexer/parser/AST for include tags, exclude tags, and score predicates
- query compiler keeps user values parameterized; only the parser's closed score-operator enum selects SQL operator text
- released-feed partial index plus tag/post indexes chosen for the initial query shapes

## Dependency decision

The v2 backend uses Go 1.25 as its minimum and `github.com/jackc/pgx/v5` 5.11.0. This avoids inheriting the legacy backend dependency surface and uses pgx directly rather than `database/sql` for PostgreSQL-specific performance and cancellation behavior.

No Redis dependency is included in this slice because the first authoritative feed/search paths do not need it. Redis should be added only for a measured ephemeral responsibility.

## API contract

Initial endpoints:

- `GET /healthz`
- `GET /api/v2/feed?before=<post-id>&limit=<n>&q=<search>`
- `GET /api/v2/posts/<id>/around?radius=<n>&q=<search>`

The service layer defaults feed visibility to `sfw` until the future authenticated request context supplies a different allowed-filter set. Secret access is therefore not exposed by the current unauthenticated skeleton.

Errors use a stable JSON envelope:

```json
{"error":{"code":"invalid_search","message":"..."}}
```

## Search grammar

Current grammar supports:

```text
cat landscape -anime score:>=100
"long tag" score:<-10
```

The lexer/parser is explicit rather than whitespace splitting. It normalizes tag case, deduplicates terms, caps complexity, and emits a typed AST. SQL compilation is separate from parsing.

## Initial schema decisions

- `bigint GENERATED ALWAYS AS IDENTITY` primary keys
- username uniqueness via `lower(username)` index; relational identity always uses `user_id`
- password credential rows are separate from users
- `user_identities` provides the future OAuth/OIDC/email provider-subject mapping without redesigning users
- content filters are small constrained values: `sfw`, `nsfp`, `nsfw`, `secret`
- post release state is explicit rather than inferred from media fields
- media processing state is explicit
- tag removals preserve who/when removed the tag
- comments are nested through immutable numeric parent IDs
- votes use one row per user/target and constrain values to `-1` or `1`
- media jobs are durable PostgreSQL rows with attempts, availability, priority, lease fields, and a partial claim index

## Performance risks to measure

Do not add indexes or caches based only on intuition. The first server run must determine:

1. whether the released-post partial ID index produces the expected bounded backward scan for normal feed pages;
2. whether rare required tags cause excessive feed-index scanning with the current correlated `EXISTS` plan;
3. whether the around-post two-sided query stays bounded around old IDs;
4. whether the initial pool cap of 8 causes contention under realistic concurrency;
5. whether query/JSON overhead remains small relative to PostgreSQL execution.

If tag search is the weak shape, change the relational/query plan before adding cache complexity.

## Validation in the Astra environment

The execution environment has Go 1.23.2 and no PostgreSQL server, while the v2 module intentionally targets Go 1.25 + pgx 5.11.0.

Validation performed here:

- all pure packages (`search`, `feed`, `httpapi`, `querysql`, `schema`) passed their tests under Go 1.23 after a temporary local-only go-directive downgrade;
- the complete source tree, including `cmd/api` and the PostgreSQL adapter, typechecked and passed tests against a temporary local-only pgx API stub;
- no stub or temporary Go-version change is committed;
- PostgreSQL migration execution and real pgx compilation remain target/server validation tasks.
