## Current prototype

The active frontend is a minimal SolidJS + TypeScript + Vite prototype using plain CSS and native browser APIs.

Implemented:

- 10,000 deterministic fake posts ordered by ID descending
- responsive 100%-width square thumbnail rows
- deterministic absolute post-index -> row mapping
- exactly one inline full-width expanded post below the selected thumbnail row
- same-row selection swaps expanded content without relocating the row
- cross-row selection relocates the expanded row
- `/post/:id`, direct load, `pushState`, Back/Forward synchronization
- Arrow keys plus J/K navigation; Escape closes the expanded post
- intrinsic image sizing and viewport-bounded video sizing
- bidirectional incremental loading in 320-post chunks
- bounded direct-link reconstruction around the selected post rather than retaining every newer post
- row-level `content-visibility` + containment with measured intrinsic row placeholders
- no virtualization

## Selection/row architecture

The prototype deliberately avoids work that would make retained-DOM profiling misleading:

- rendered rows are keyed by stable absolute numeric row index rather than freshly allocated row arrays;
- adding retained posts only adds new row keys instead of recreating every existing row;
- Solid `createSelector` is used for selected-post and selected-row membership, so a selection change should notify only the old/new post and old/new row subscribers rather than every retained thumbnail;
- a far route/history jump recenters a bounded synthetic window instead of expanding one giant prefix range;
- top and bottom `IntersectionObserver` sentinels extend the loaded range while preserving absolute row identity;
- sticky-header backdrop blur was removed so the prototype does not add avoidable scroll repaint cost.

## Explicit prepend anchoring

The first client profiling run found a reproducible correctness defect when newer rows were prepended from a centered deep link such as `/post/5000`: the selected/visible content moved far away from its prior viewport position.

`astra/m1-scroll-anchor` addresses this without virtualization or retention changes:

1. before a top-edge range extension, capture the row currently under the viewport just below the sticky header;
2. fall back to the selected row if no visible row can be sampled;
3. prepend the new range using the existing stable absolute row keys;
4. on the next animation frame, measure how far that same DOM row moved;
5. scroll by exactly that delta before paint;
6. disable native `overflow-anchor` inside the board so the browser does not compete with the explicit correction;
7. coalesce overlapping prepend requests until the two-frame correction/probe completes.

This is intentionally a viewport-preservation mechanism, not a selected-post-specific scroll hack. If the user has scrolled away from the selected post, the currently visible row remains the anchor.

## Benchmark API

`window.__ginbarM1` is always exposed:

- `select(id)` selects through the normal route/selection path;
- `retain(count)` prepares a retained prefix for profiling and resolves after two animation frames;
- `prepend()` prepends one 320-post chunk using the production anchor path and resolves with `beforeTop`, `shiftedTop`, `afterTop`, and applied correction;
- `run("same-row" | "cross-row", iterations?)` measures sequential selections;
- `runMatrix(iterations?)` runs 320 / 2,000 / 5,000 / 10,000 retained-post scenarios;
- `snapshot()` returns columns, logical range, rendered rows/thumbnails, DOM node count, row mount/unmount counters, Long Tasks, and Chromium heap when available;
- `assertInvariants()` checks selected-thumbnail / expanded-row consistency;
- `resetStats()` and `stats()` manage/read the rolling instrumentation state.

Adding `?bench=1` displays the instrumentation panel and also measures normal click/keyboard selections. Omit it for the cleanest automated matrix/profile.

Selection timing has two values:

- `syncMs`: local selection state/DOM propagation before requesting the next frame;
- `frameMs`: elapsed time until the next `requestAnimationFrame`, which includes display scheduling and is not pure scripting time.

DevTools Performance remains the source of truth for scripting/layout/paint attribution.

## Existing profiling evidence

The first full browser/client run tested `astra/m1-board-prototype` at `da0885f724d662333af45dc307c1d501135da266` and is documented on `astra/m1-hardware-results`.

Highlights:

- real `npm install`, `npm run validate`, tests, typecheck, and production build passed;
- production JS was 26,539 B raw / 10,122 B gzip; CSS was 3,293 B raw / 1,402 B gzip;
- selection sync p95 stayed roughly 0.4-0.5 ms through 10,000 retained posts on the Windows client browser;
- 10,000 posts retained about 32.5k DOM nodes at 1440x900 and about 40k at 390x844;
- direct routes, history, keyboard navigation, bounded deep links, and full traversal passed;
- prepend anchoring failed and is the correctness issue addressed by the current branch.

Frontend/browser timing belongs to the client machine executing the browser. The remote target server is authoritative only for later backend/server-side benchmarks.

## Validation of the anchor implementation in this session

- the exact committed `App.tsx` blob passed a TypeScript 5.8.3 source check using local Solid declaration stubs;
- a framework-free Chromium forced-layout harness inserted 10,000 px above a viewport anchor with native anchoring disabled; explicit compensation restored the anchor with 0 px residual error;
- the current branch changes only `App.tsx`, `styles.css`, and M1 handoff/docs; no virtualization or retention behavior was added.
