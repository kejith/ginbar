# M1 board performance prototype

Status: in progress
Branch: `astra/m1-board-prototype`

## Current slice

The first M1 slice replaces the active frontend entry/config with a minimal SolidJS + TypeScript + Vite prototype while leaving the legacy backend/worker untouched.

Implemented:

- 10,000 deterministic fake posts, ordered by ID descending
- responsive 100%-width square thumbnail rows
- deterministic post-index -> row mapping
- exactly one inline expanded post below the selected thumbnail row
- same-row selection swaps expanded content in place
- cross-row selection relocates the expanded row
- `/post/:id`, direct load, `pushState`, and Back/Forward synchronization
- Arrow keys plus J/K navigation; Escape closes the expanded post
- image sizing with intrinsic dimensions; video constrained by `100svh`
- incremental retention in 320-post chunks via `IntersectionObserver`
- row-level `content-visibility` + containment; no virtualization yet
- in-app selection timing and Long Tasks instrumentation behind `?bench`

The core model is plain checked JavaScript so Node can test layout/history math without a DOM or frontend test framework.

## Instrumentation

With `?bench` enabled the app exposes `window.__ginbarM1`:

- `select(id)` selects a post through the normal UI path
- `retain(count)` sets the retained synthetic post count for profiling
- `run("same-row" | "cross-row", iterations?)` runs sequential selection samples
- `stats()` returns the rolling selection samples and observed long-task count

Selection latency is sampled from local state mutation to the next `requestAnimationFrame, which approximates whether the update is ready for the next paint. DevTools Performance remains the source of truth for scripting/layout/paint breakdowns.

## Architectural lower-bound baseline

A framework-free DOM harness using the same row grouping and CSS containment strategy was measured in headless Chromium in the Astra execution environment. Each sample removed/inserted the one expanded row and forced layout with `getBoundingClientRect()`. These numbers intentionally exclude Solid runtime/compiler overhead and are **not** the framework-gate result.

| Viewport | Retained thumbnails | Same-row p95 | Cross-row p95 |
| --- | ---: | ---: | ---: |
| 1440x900 | 320 | 0.2 ms | 0.3 ms |
| 1440x900 | 5,000 | 0.8 ms | 1.1 ms |
| 390x844 | 320 | 0.2 ms | 0.4 ms |
| 390x844 | 5,000 | 1.7ms | 1.9 ms |

The baseline suggests row grouping + containment is not itself an obvious bottleneck at M1 scale. It does not justify retaining 5,000+ DOM nodes indefinitely; real Solid long-scroll profiling must decide whether a retention cap or virtualization is warranted.

## Verification completed in this slice

- `node --test src/board-model.test.js`: 5/5 passing
- TypeScript source checked with local declaration stubs because this execution environment cannot reach the npm registry; no source-level type errors were found
- real `npm install`, Vite production build, and Solid runtime browser profile were not executable in this environment and remain required before the M1 framework decision

## Next evidence required

Run the real Solid app with installed dependencies and capture desktop/mobile-class profiles for:

1. cold/direct `/post/:id`
2. same-row and cross-row `window.__ginbarM1.run(...)`
3. Back/Forward and keyboard navigation
4. progressive retention at 320, 2,000, 5,000, and 10,000 posts
5. long scrolling, DOM count, heap growth, and long tasks

Only add virtualization if those profiles identify retained DOM as the bottleneck and inline-row behavior remains correct.
